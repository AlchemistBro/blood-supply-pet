# Сообщения в DLT, outbox растёт, consumer отстаёт

Обмен между сервисами — outbox → ретранслятор → топик → consumer → inbox (ADR-0003, `libs/messaging`).
Consumer повторяет обработку с паузой; после исчерпания попыток или при постоянной ошибке (`IsPermanent`) запись
уходит в `<топик>.dlt`, а обработка остальных продолжается. Значит, **действие по этому сообщению не выполнено**:
статус не сменился, письмо не ушло, закрепление не снято.

## Сигналы

| Алерт | Что значит |
| --- | --- |
| `bs-dlt-not-empty` | в DLT есть новая запись (`messaging_consumer_dead_letters_total`) |
| `bs-outbox-stuck` | старейшая строка outbox старше минуты пять минут подряд |
| `bs-consumer-lag` | consumer-группа отстаёт больше чем на 500 сообщений (демо) |

Дашборд «АС: обмен сообщениями». Метрики `messaging_*` появятся в этапе 8 (см. `deploy/observability/README.md`);
до этого DLT виден по журналу сервиса: `"msg":"сообщение отправлено в DLT"` с полями `type`, `id`, `attempts`, `err`.

## DLT не пуст

1. Найдите запись: Kafka UI (`docker compose --profile ui up -d kafka-ui`, http://localhost:8090), топик
   `<исходный топик>.dlt`. Или из контейнера Kafka:
   ```
   kafka-console-consumer.sh --bootstrap-server kafka:29092 --topic transfer.events.dlt --from-beginning \
     --property print.headers=true --property print.key=true --max-messages 10
   ```
2. Заголовки: `message-type`, `message-id`, `correlation-id`, `dlt-error` (причина), `dlt-source-topic`.
   По `correlation-id` найдите трассу в Grafana (Tempo) и строки журнала сервиса-получателя.
3. Разберите причину:
   - **нет обязательных заголовков / не разбирается схема** — ошибка отправителя или контракта (`libs/contracts`).
     Исправление — в отправителе; запись не переигрывать, пока причина не устранена;
   - **временная ошибка, исчерпаны попытки** (база, сеть) — устраните причину, затем переиграйте;
   - **ошибка бизнес-логики получателя** — заведите дефект; оцените, что не выполнено (по `message-type` и `events.md`).
4. Переиграть запись — опубликовать её **без изменений** (ключ, значение, все заголовки, кроме `dlt-*`) обратно в
   исходный топик. Повтор безопасен: inbox получателя отсекает дубль по `message-id`. Отдельного инструмента пока нет:
   Kafka UI («Produce message») или `kcat`. Запишите в журнал смены, что и когда переиграно.
5. Не удаляйте DLT-записи: хранение 30 суток (`deploy/k8s/base/platform/kafka/topics.txt`), это след для разбора.

Особо: запись `transfer.commands` или `transfer.events` в DLT может означать, что обязательство на передачу застряло
в промежуточном статусе. Сообщите дежурному смены: возможно, нужна ручная перевозка или эскалация.

## Outbox растёт

Ретранслятор останавливается на первой ошибке отправки и повторяет с той же строки (порядок важнее скорости).
1. Журнал сервиса: `component=outbox-relay`, ошибка отправки.
2. Kafka жива? `docker compose ps kafka` / `kubectl -n bs-app get pods`; топик существует (Job создания топиков)?
3. Ретранслятор один на базу (advisory lock): если реплик несколько, работает одна — это норма.
4. После устранения причины outbox выгружается сам; новых действий не нужно.

## Consumer отстаёт

1. Сервис-получатель жив и не перезапускается? (`/readyz`, рестарты пода.)
2. Долгая обработка (p95 на дашборде) — чаще всего блокировки в базе; смотрите трассы.
3. Ребаланс по кругу — проверьте, не превышает ли обработка пачки таймаут сессии группы.
