# Этап 5. Планирование пополнения (ФП3)

Цель: `planning` закрывает FR021–FR028, FR035; NFR002, NFR009, NFR010, NFR013, NFR014. Имитатор C02. Бенчмарк.
Это сердце «инновационности» проекта: план по прогнозу ЧС до поступления пострадавших.

## Чеклист

### Прогноз ЧС (ИНТ-02)
- [ ] `sim-emergency`: формирует прогноз по сценарию (территория, период, строки вид × группа × объём, принимающие клиники с долями или без них), `POST` в `planning` через nginx; dev-панель «отправить прогноз» с вариантами «с ПДн» (для демонстрации фильтра) и «без принимающих клиник».
- [ ] Входной адаптер с белым списком (NFR010): `DisallowUnknownFields` + явный фильтр; `scenario_version` уникальна; `EmergencyForecastAccepted`; квитанция в ответе.
- [ ] Распределение сценарной потребности (FR024): по принимающим клиникам из прогноза; иначе по долям «район → клиника» с `is_rough_estimate = true`; коррекция оператором (`adjusted_by`, `adjust_reason`, аудит).

### Проекции
- [ ] `stock_projection` (снимки + норматив, водяной знак), `demand_projection` (опубликованная версия), `delivery_estimate_projection`, `obligation_projection`; пересборка проекции командой `task planning:rebuild`.

### Расчёт плана
- [ ] Целевой запас (FR021, FR023): `target = norm + background + emergency` по клинике × вид × группа.
- [ ] Защищённый объём источника (FR025, NFR013): норматив + фон источника за период + подтверждённые обязательства; публикация `ProtectedVolumePublished` через `inventory` (команда) или напрямую событием — решить в ADR-0015 (допущение: planning публикует событие `ProtectedVolumeCalculated`, inventory ретранслирует как владелец запаса).
- [ ] Подбор источников (FR026): кандидаты с избытком над защищённым объёмом, сравнение по подтверждённому запасу и времени доставки; жадный алгоритм с объяснением факторов; `fallback_sources` для эскалации.
- [ ] План: `ReplenishmentPlanBuilt` с `coverage_ratio`, `elapsed_ms`; предложения `TransferProposed` → команда `OpenObligation` в `transfer` (идемпотентно по `proposal_id`); непокрытое → `PlanDeficitRecorded` (NFR014: всегда).
- [ ] Реестр дефицита O11: собственные записи + проекция `RequestDeficitRecorded` из `matching`.
- [ ] Пересчёт плана при новой версии оценки или прогнозе: старые `PENDING` предложения → `CancelObligation` (`план пересчитан`).
- [ ] OpenAPI: `POST /int/forecast` (ИНТ-02), `GET /forecasts`, `PATCH /forecasts/{id}/lines/{lineId}`, `POST /plans` (построить), `GET /plans`, `GET /plans/{id}` (целевые, предложения, статусы, объяснения, версии входов), `GET /deficits`.

### Бенчмарк NFR002
- [ ] `task bench:plan`: 100 клиник, 100 000 единиц, 12 районов, 4 вида, 8 групп → план ≤ 30 с на CI-раннере; результат в `docs/perf/`.
- [ ] Профилирование и индексы по результатам.

### UI оператора и дежурного
- [ ] «Прогнозы ЧС»: список, строки, пометка «грубая оценка», коррекция строки с причиной.
- [ ] «План пополнения»: целевой запас по клиникам, предложения со статусами O07 (live), покрытие, дефицит, «Почему этот источник» (объяснение), версии входов (оценка, прогноз, водяной знак).
- [ ] «Реестр дефицита»: фильтры по типу (план/заявка), причине, клинике.

### Тесты
- [ ] Свойственные (rapid): ни одно предложение не опускает источник ниже защищённого объёма; покрытие ≥ 0,9 либо есть запись дефицита; сумма предложений не превышает целевой объём.
- [ ] NFR010: прогноз с `snils`, `full_name`, `patients[]` принят без них; в БД, логах и трассах их нет (grep по дампу).
- [ ] Интеграционные: предложение → `transfer` открывает O07 → статус возвращается в план; пересчёт отменяет PENDING.

## Критерий выхода
Демо: имитатор C02 присылает прогноз → план за ≤ 30 с для 100 клиник → предложения уходят операторам → ни одна передача не нарушает защищённый объём → непокрытое в реестре дефицита. Бенчмарк зелёный в nightly.

## Проверка «тест действительно проверяет»
Убрать слагаемое «подтверждённые обязательства» из защищённого объёма → свойственный тест падает.
