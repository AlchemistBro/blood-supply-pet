# Этап 2. Интерфейс и вход

Цель: сервис `web` с OIDC-входом через Keycloak и экранами оператора по заданиям; стиль гос-системы; живые статусы.
Требования: FR043 (статус задания), FR048 (экран подтверждения), FR049 (причины), NFR011, NFR015 (водяной знак), NFR016 (каркас).
Спецификация UI: `docs/ui/style-guide.md`, `docs/ui/screens.md`.

## Чеклист

### Вход и сессия
- [ ] OIDC code + PKCE с Keycloak (`coreos/go-oidc`), callback, refresh, logout с end-session; сессия в `securecookie`.
- [ ] Страница входа в стиле гос-портала с блоком «Демо-доступ»: кнопки «Войти как врач / оператор клиники № 1 / аналитик / дежурный» (переход в Keycloak с подставленным логином через `login_hint`).
- [ ] Middleware: требуемая роль на маршрут, `clinic_id` в контексте, 403-страница «Недостаточно прав» с записью `DENIED` в аудит.
- [ ] Передача JWT в сервисы; обработка 401 от сервиса → повторный вход.

### Каркас UI
- [ ] Базовый layout: шапка (герб-заглушка, название АС, роль, ФИО/логин, клиника, кнопка выхода), левая навигация по роли, хлебные крошки, подвал с версией и пометкой «демонстрационные данные».
- [ ] Компоненты шаблонов: таблица с сортировкой (server-side), пагинация, бейдж статуса O07 (цвета по style-guide), форма с ошибками полей, модальное подтверждение (HTMX + `<dialog>`), тосты, пустые состояния.
- [ ] Индикатор NFR015 в шапке: «Запас обновлён HH:MM» (из `inventory` `GET /sync/last`), предупреждение при превышении порога.
- [ ] Статика: собственный CSS (переменные палитры, типографика, таблицы, формы), HTMX 2.x вендорен, без внешних CDN.
- [ ] Доступность: семантика, фокус, контраст AA; все формы работают без JS.

### Экраны оператора (этап 2)
- [ ] «Задания на передачу»: список O07 своей клиники-источника по статусам, таймер до срока, срочность; фильтры; HTMX-опрос или SSE для обновления строк.
- [ ] Карточка задания: параметры, спецификация (без фенотипа для оператора — только «есть/нет требований»), список подходящих единиц FEFO (из `inventory` по копии), выбор единиц чекбоксами, флаг «подтвердить частично», кнопка «Подтвердить передачу» → результат в том же запросе человеческим языком (все 8 результатов `ConfirmationResult`).
- [ ] Действия: «Заменить единицу» (выбор кандидата, результаты `ReplacementResult`), «Отказать» с причиной.
- [ ] История задания (аудит по объекту) на карточке.

### Живые статусы
- [ ] `web` consumer `transfer.events` → SSE `/events/obligations?clinic=` → HTMX `sse-swap` обновляет бейджи и таймеры.

### Тесты
- [ ] Golden-тесты шаблонов; `httptest` формы без JS (подтверждение, замена); тест 403 по ролям; Playwright: вход через Keycloak и подтверждение задания с скриншотами (`docs/architecture/diagrams/screenshots/`).
- [ ] e2e: оператор подтверждает в браузере → статус `TRANSPORT_REQUESTED` появляется без перезагрузки.

## Критерий выхода
Демо: открыть `https://localhost`, войти как оператор клиники № 1 через Keycloak, увидеть задание, подтвердить две единицы,
увидеть «Закреплено, готовьте к отправке», статус меняется на «Перевозка запрошена» без перезагрузки.
