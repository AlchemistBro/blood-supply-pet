# План разработки: АС распределения компонентов донорской крови на Go

Статус: план утверждён владельцем проекта 20.10.2026.
Источник канона: учебный проект РТУ МИРЭА (ПР2–ПР6 по дисциплинам «Архитектура микросервисов» и DDD, версия v12)
и Java-прототип саги подтверждения (`миграция_микросервисы/blood-supply`). Канон перенесён в `docs/domain/`.

## 1. Цель

Построить **production-ready** реализацию АС на Go в микросервисной архитектуре по карте контекстов v12,
с простым веб-интерфейсом в стиле государственной медицинской системы, полным набором тестов, CI/CD и
развёртыванием в Kubernetes. Проект публичный (пет-проект), поэтому код, документация, схемы (C4, UML, BPMN)
и README должны быть такого качества, чтобы их можно было показывать как портфолио архитектора.

Что система делает (одной фразой из защиты): *не ждёт, когда кровь закончится, а заранее распределяет её по прогнозу ЧС*.

## 2. Решения, зафиксированные владельцем (20.10.2026)

Подробно: `docs/architecture/c4-containers.md`, `docs/architecture/events.md`, `docs/architecture/data-model.md`.

| Сервис | Контекст DDD | ФП / объекты | БД | Порт |

Платформа: PostgreSQL 16 (один экземпляр, база и роль на сервис), Apache Kafka (KRaft, один брокер),
Keycloak, OpenTelemetry Collector + `grafana/otel-lgtm`, Nginx (compose) / ingress-nginx (k8s).

### 3.2 Правила взаимодействия

1. Между сервисами только события и команды через Kafka: transactional outbox → ретранслятор → топик → inbox.
   Ключ сообщения — идентификатор агрегата, поэтому сообщения по одному агрегату упорядочены.
2. Единственный синхронный вызов между сервисами: `transfer → inventory` «статус единиц» перед транзакцией
   подтверждения (ADR-0004): таймаут 3 с, предохранитель, вне блокировок.
3. `web` ходит в сервисы по HTTP/JSON (OpenAPI у каждого сервиса), передаёт JWT пользователя; сервисы проверяют
   подпись по JWKS Keycloak и права роли.
4. Сервис пишет только в свою базу. Чужие данные держит как проекцию из событий с версией (водяной знак).
5. Персональных данных пациентов и пострадавших в системе нет: в заявке только номер случая клиники (K1);
   прогноз ЧС проходит через белый список полей (NFR010).

### 3.3 Сага подтверждения передачи (ядро)

Перенос из Java-прототипа без изменения семантики, кроме отступлений из ADR-0027: `docs/domain/obligation-states.md`,
`docs/architecture/saga-confirmation.md`. Четыре гонки (защищённый объём, выдача во время подтверждения,
позднее подтверждение после эскалации, замена против подтверждения) — обязательные фитнес-тесты каждого этапа.

## 4. Этапы

Каждый этап описан в `docs/tasks/NN-*.md` чеклистом с критерием выхода. Этап считается закрытым, когда
чеклист выполнен, CI зелёный, демо из критерия выхода воспроизводится одной командой, документация и схемы обновлены.

| Этап | Название | Что появляется | Критерий выхода (демо) |
| --- | --- | --- | --- |
| 0 | Фундамент | Монорепозиторий, Taskfile, compose платформы, `libs/` (messaging, contracts, httpx, observability, refdata), CI, канон в `docs/`, README | `task up` поднимает платформу; `task ci` зелёный; тест outbox → Kafka → inbox проходит на Testcontainers |
| 1 | Сага через сеть | `transfer`, `inventory` (минимум: копия единиц, статус, события), `logistics-gateway`, `sim-aist`, `sim-logistics` | Четыре гонки зелёные; `kill -9 logistics-gateway` посреди заказа → сверка без второго заказа; smoke-скрипт саги |
| 2 | Интерфейс и вход | `web`: Keycloak OIDC, стиль, экраны оператора по заданиям, HTMX/SSE | Оператор входит через Keycloak, подтверждает задание в браузере, видит статус до TRANSPORT_REQUESTED без перезагрузки |
| 3 | Запасы полностью | `inventory`: ActualStock, годовой расход и норматив, SyncRun, FEFO, FR050, суточная сверка, NFR015; экраны запаса | Экран запаса клиники с нормативом и временем обновления; «Обновить из АИСТ-М» показывает результат; «ниже норматива» подсвечено |
| 4 | Территориальная потребность | `demand`: три вида CSV, проверка с построчными ошибками, история расхода, доли, версии оценки, публикация; экраны аналитика | Аналитик загружает CSV, видит отклонённые строки, рассчитывает и публикует версию; событие доходит до `planning` |
| 5 | Планирование | `planning`: приём прогноза ЧС (белый список), целевой запас, подбор источников с защищённым объёмом, план, предложения в `transfer`, дефицит; `sim-emergency`; бенчмарк NFR002 | План для 100 клиник и 100 000 единиц ≤ 30 с; ни одной передачи ниже защищённого объёма (NFR013); покрытие ≥ 90 % или дефицит (NFR014) |
| 6 | Заявка врача | `matching`: заявка K1, ограничения, правила O15 с версиями, варианты с объяснением, выбор → задание; аудит чтения номера случая; экраны врача | Врач вводит заявку, видит ранжированные варианты с объяснением, выбирает удалённый, оператор источника получает задание |
| 7 | Уведомления и аудит | `notification` (Mailpit), эскалации дежурному, `audit` с цепочкой хешей, экраны дежурного и ИТ-службы | Письмо оператору о срочном задании; эскалация по таймеру; разрыв цепочки аудита обнаруживается проверкой |
| 8 | Kubernetes | kind, kustomize (base/local/ci), CloudNativePG с PITR, Kafka, Keycloak, ingress, probes, HPA, NetworkPolicy по сегментам, CD в kind из CI | `task k8s:up` разворачивает всё в kind; e2e smoke проходит в CI на kind; restore-drill: RTO ≤ 60 мин, RPO ≤ 15 мин |
| 9 | Закалка и витрина | k6 (NFR003 p95 ≤ 2 с), хаос-сценарии, trivy/govulncheck/gosec, финальные C4/UML/BPMN, скриншоты, демо-сценарий | README с демо, все схемы актуальны, CI со всеми проверками зелёный, релиз образов в ghcr.io с SBOM |
| 10 | Демо-стенд на Railway | Публичный стенд из образов ghcr.io, облегчённый профиль | Рабочий публичный URL, README ссылается на стенд, демо-сценарий проходит |

Порядок этапов 3–7 допускает перестановку, этапы 0–2 строго по порядку. Этап 8 можно начать параллельно с 5–7,
когда стабилен состав сервисов.

## 5. Технологический стек (решено, см. ADR-0012)

| Слой | Выбор | Почему |
| --- | --- | --- |
| Язык | Go 1.27, один `go.mod` на монорепозиторий | Атомарные рефакторинги контрактов; `internal/` каждого сервиса закрыт компилятором |

| Сообщения | `franz-go` | Идемпотентный продюсер, ручной коммит оффсетов, производительность |
| UI | `html/template` + `embed`, HTMX 2.x (вендорится), собственный CSS | Один бинарник, стиль гос-системы |
| Вход | Keycloak 26, `coreos/go-oidc`, PKCE, сессия в зашифрованной cookie | Стандартный OIDC, роль и `clinic_id` как claim |
| Наблюдаемость | `slog` JSON, OpenTelemetry (трассы, метрики, логи), `grafana/otel-lgtm` | correlation id сквозь Kafka-заголовки |
| Тесты | `testing`, `testcontainers-go`, `go test -race`, k6 | Реальные PostgreSQL и Kafka в тестах, как в Java-прототипе |
| Сборка | Taskfile (`go-task`), многостадийные Dockerfile на distroless | Кросс-платформенно для Windows |
| CI/CD | GitHub Actions, ghcr.io, cosign, syft (SBOM), dependabot | Публичный репозиторий |
| Kubernetes | kind, kustomize, CloudNativePG, Kafka одним Deployment (без Strimzi), ingress-nginx | Минимальная эксплуатационная сложность для пет-проекта с продовыми практиками |

## 7. Риски и как с ними работаем

| Риск | Снижение |
| --- | --- |
| Объём: 9 сервисов + UI + k8s для одного разработчика | Строгая этапность, каждый этап даёт демо; имитаторы простые; сервисы `notification` и `audit` минимальны |
| Расползание границ контекстов | Правило «пишет только владелец», `internal/` компилятором, тест на импорты в CI, контракты только через `libs/contracts` |
| Сага сложнее, чем кажется | Перенос из Java-прототипа 1:1, тесты гонок переносятся первыми (красные → зелёные) |
| Kubernetes съедает время | Этап 8 после работающего compose; только kind и kustomize; без service mesh |
| Клинические правила O15 | Содержание правил синтетическое с пометкой «демо»; структура и версионирование настоящие (ADR-0010) |
| Расхождение с учебными документами (Java, монолит) | ADR-0001, ADR-0002 объясняют; README честно ссылается на документы как источник канона |
