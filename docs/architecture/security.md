# Безопасность и доступ

## Идентификация (Keycloak, OIDC)

- Realm `blood-supply`, клиент `web` (confidential, Authorization Code + PKCE), клиент `services` (client credentials, роль SERVICE). `blood-supply-cli` с password grant используется только для демо и проверок.
- Роли realm: `PHYSICIAN`, `CLINIC_OPERATOR`, `TERRITORIAL_ANALYST`, `DUTY_OFFICER`, `IT_SERVICE`.
- Атрибут пользователя `clinic_id` → claim `clinic_id`; роли → claim `realm_access.roles`; `preferred_username` используется как `user_id` в аудите.
- Дополнительная проверка OTP настраивается политикой входа Keycloak; в демонстрационном realm она не включена.
- `web` хранит сессию в зашифрованной cookie (`SameSite=Lax`, `Secure`, `HttpOnly`), обновляет access token по refresh token, при выходе вызывает end-session Keycloak.
- Отказ раннего refresh не отзывает ещё действующий access token и не продлевает его срок. При истечении токена или смене участника нужен новый вход. Перед новым входом web проверяет discovery с бюджетом 1,5 с; отказ показывает страницу 503 с Retry-After, без перенаправления на недоступный провайдер.
- Сервисы проверяют JWT (подпись по JWKS с кэшем, `iss`, `aud`, `exp`) в middleware `libs/httpx/auth`; внутренние вызовы (`transfer → inventory`) идут с сервисным токеном (client credentials) и помечены `X-Internal-Call`.

## Авторизация

Матрица «роль → операция» в `libs/httpx/auth/policy.go`, одна на всю систему, проверяется в каждом сервисе:

| Операция | PHYSICIAN | CLINIC_OPERATOR | TERRITORIAL_ANALYST | DUTY_OFFICER | IT_SERVICE |
| --- | --- | --- | --- | --- | --- |
| Просмотр запаса своей клиники | ✓ | ✓ | — | ✓ (все) | ✓ |
| Ввод годового расхода, FR050 | — | ✓ (своя клиника) | — | — | — |
| Загрузка CSV, публикация оценки | — | — | ✓ | — | — |
| Просмотр плана, коррекция прогноза (FR024) | — | ✓ | ✓ (просмотр) | ✓ | — |
| Подтверждение / замена / отказ по заданию | — | ✓ (источник = своя клиника) | — | ✓ | — |
| Создание заявки, выбор варианта, отмена | ✓ (своя клиника) | — | — | — | — |
| Чтение `patient_case_no` | ✓ (своя заявка) | ✓ (задание по заявке, только при подтверждении) | — | — | — |
| Эскалации, ручная перевозка | — | — | — | ✓ | — |
| Правила подбора O15 (версии) | просмотр | — | — | — | ✓ |
| Журнал аудита | — | — | — | ✓ | ✓ |
| Dev-панель имитаторов | только профиль `dev` | | | | |

Проверка клиники: `clinic_id` из токена сравнивается с клиникой объекта; несовпадение → 403 и запись `DENIED` в аудит.
Числовой claim разбирается без float64: положительный int64 без дроби, переполнения и округления.
Строковый атрибут Keycloak и одноэлементный массив поддерживаются.

## Данные класса K1

- `patient_case_no` шифрует приложение (`libs/k1seal`, ADR-0020). Конверт хранится в `matching` (`clinical_request_patient`)
  и в `aist_outbox_message.payload` (`inventory`, до квитанции АИСТ-М, затем затирается). Ключ `BS_K1_KEYS` есть только
  у `matching` и `inventory`; `transfer`, Kafka, outbox, аудит и журналы видят только конверт.
- Показ номера — только `web` → `matching` `GET /requests/{id}/patient-case`: `matching` проверяет роль и клинику
  (оператору — если его клиника источник активного задания по заявке), в одной транзакции пишет `READ_PATIENT_CASE`
  и только затем отдаёт номер. `web` получает его по HTTP (TLS в k8s) лишь для экрана: не хранит, не логирует, ключа не имеет.
- Открытым текстом номер не попадает никуда: ни в события и команды, ни в логи, трассы, письма, объяснения вариантов.
  Конверт (`patient_case_sealed`, рядом `request_id`) есть только в командах `OpenObligation` и `AllocateUnitsToPatient`.
- Каждое чтение — `READ_PATIENT_CASE` в аудит (NFR016), пишет только `matching` при выдаче номера; `web` эту запись
  не дублирует, а свой отказ до запроса к `matching` пишет как `ACCESS_DENIED`. Каждое изменение заявки — аудит
  с участником (NFR008).
- Спецификация замены (фенотип) — квазиидентификатор: не логируется, не уходит в письма.

## NFR010: белый список полей прогноза ЧС

Входной обработчик `planning/internal/api` оставляет из тела ИНТ-02 только поля белого списка и отбрасывает
всё остальное, затем проверяет результат по схеме `libs/contracts/schemas/int02/EmergencyForecast.v1.json`
(`additionalProperties: false` на каждом уровне; тип `int02.EmergencyForecast`, реестр `contracts.Inbound`). Белый список
(все поля без ПДн):

- `scenario_version`, `scenario_kind?`, `scenario_name?`, `demo?`;
- `territory{name, districts[]?{district_code, weight}}` — название территории и районы справочника с весами;
- `period_start`, `period_end`;
- `lines[]{clinic_code?, component_kind, blood_group?, volume_ml, share?}`.

Сведения о пострадавших (`snils`, `full_name`, `patients[]` и любые другие поля вне списка) схема не описывает: тест —
запрос с такими полями принимается без них, в БД и логах их нет.

## Платформа

- TLS на входе (nginx / ingress), внутри кластера plain HTTP с NetworkPolicy; mTLS для ИНТ-05 в проде (в демо отключено, флаг).
- Kafka: демонстрационный брокер без аутентификации; SASL/SCRAM и ACL для рабочего окружения требуют отдельной настройки брокера и клиентов.
- PostgreSQL: роль на сервис, запрет чужого подключения; `audit_record` защищён триггером от UPDATE/DELETE, целостность проверяется цепочкой. Администратор БД может обойти триггер; такой сценарий проверяется детектором разрыва.
- Образы distroless без shell, non-root, read-only FS; `govulncheck`, `trivy`, `gosec` в CI; dependabot.
- Секреты: `.env.example` и kustomize `secretGenerator` с демо-значениями; настоящие секреты никогда в git (gitleaks в CI).
- Лимиты частоты на ingress для `/auth` и `/api/int/forecast`.

CSP без inline/eval, frame-ancestors none, no-store и HSTS при TLS/X-Forwarded-Proto=https.
Cookie всегда HttpOnly/SameSite=Lax; Secure управляется BS_COOKIE_SECURE (включён по умолчанию).
Экранирование пользовательских строк, state/nonce/PKCE и запрет открытых перенаправлений проверены тестами.

Это проверка исходников и локальных сценариев. Trivy образов, работающая конфигурация платформы,
браузерная и сквозная приёмка остаются открытыми; контейнеры и деплойные тесты не запускались.

Для клиента web нужен default scope basic (идентификатор sub в access token) и отдельный mapper
preferred_username; profile/email исключены. Существующий realm автоматически не обновляется
повторным импортом: [устранение ошибки входа](../runbooks/keycloak-login.md).
