# Демонстрация Blood Supply

Сценарий подготовлен по коду и контрактам на 24.10.2026. На работающем стенде он ещё не пройден.
Локальные тесты и проверки безопасности выполнены отдельно: [состояние приёмки](perf/acceptance-status.md).
Данные, нормативы и правила подбора синтетические. Время показа — около пяти минут после подготовки.

## Подготовка

Нужна отдельная локальная машина или согласованный стенд с Docker, Go 1.27.3+ и Task.
Команды ниже меняют демонстрационный стенд. На текущей рабочей машине с ограничением деплойных тестов
они не выполнялись; для просмотра документации запуск не требуется.

Из корня репозитория, в Git Bash на Windows или shell на Linux:

```bash
task up
task seed
```

`task up` создаёт `deploy/compose/.env` из примера, если файла ещё нет, и поднимает профиль services.
Утилита seed работает через HTTP API; подробно — [наполнение](../tools/seed/README.md).
Успех — завершающее сообщение «Демо подготовлено» с `plan_id` и `request_id`, а не только запуск контейнеров.
Сохраните эти два идентификатора для переходов `/plans/{plan_id}` и `/requests/{request_id}`.
При ошибке seed подготовка не завершена: сначала разберите сообщение, затем повторите команду.

Что подготовлено по реализации seed:

| Данные | Содержание |
| --- | --- |
| Запас | 10000 синтетических единиц дополнительно к стартовому набору имитатора АИСТ-М; ожидается успешная синхронизация |
| Нормативы | Добавляются недостающие; существующие значения сохраняются |
| Потребность | Три CSV, годовая оценка и её публикация |
| Прогноз | Первый день следующего месяца UTC; RBC O+, 900 мл, получатель C002 |
| План | Строится после получения опубликованной оценки в проекции planning; наличие предложения из конкретной клиники не гарантируется |
| Заявка | Врач клиники C002, RBC O+, 1 единица, URGENT; выбор остаётся за пользователем |

Повтор seed не сбрасывает состояние уже выбранной заявки, подтверждённых заданий или нормативов.
Для повторного показа создайте новую синтетическую заявку через UI; очистка БД и `task down` для этого не нужны.
Не используйте `task down` как обычное завершение: эта задача удаляет тома.

Откройте `https://localhost`. Compose создаёт самоподписанный сертификат localhost; браузер может запросить
подтверждение доверия этому локальному сертификату. Основной показ проходит через HTTPS из-за Secure-cookie.
Keycloak для входа доступен на `http://localhost:8180`, Mailpit — на `http://localhost:8025`.
Разные роли удобнее открыть в отдельных профилях браузера; вкладки одного профиля разделяют сессию.

Kafka UI для основного показа не нужен. При отдельной необходимости его подготовленная команда:

```bash
docker compose -f deploy/compose/compose.yaml --env-file deploy/compose/.env --profile ui up -d kafka-ui
```

Адрес Kafka UI — `http://localhost:8090`. Нагрузка, хаос и Kubernetes для этого сценария не запускаются.

## Учётные записи

Пароль всех перечисленных демонстрационных пользователей — `demo`. Соответствие сверено с realm compose.

| Пользователь | Роль | Клиника | Что показать |
| --- | --- | --- | --- |
| `analyst1` | Аналитик | Вся территория | CSV, оценка потребности, планы и дефициты |
| `physician1` | Врач | C002, ID 2 | Заявка, варианты, выбор и отдельное чтение номера случая |
| `operator-c001` | Оператор | C001, ID 1 | Запас, FEFO, подтверждение и отправка из C001 |
| `operator-c002` | Оператор | C002, ID 2 | Приёмка поставки в C002 |
| `duty1` | Дежурный | Все клиники | Задания других источников, перевозка и эскалации |
| `it1` | ИТ-служба | Все клиники в рамках роли | Аудит, проверка цепочки и состояние интеграций |

`physician1` не относится к C001. Для него вариант C002 местный: он не создаёт демонстрируемую
межклиническую перевозку. Для передачи C001 → C002 выбирайте удалённый вариант с источником C001.

## Основной показ

| Время | Действие | Ожидаемый результат |
| --- | --- | --- |
| 0:00–1:00 | `analyst1`: `/demand`, затем `/plans/{plan_id}` | Видны входные CSV, опубликованная оценка и план с объяснениями, защищённым объёмом и дефицитом |
| 1:00–2:00 | `physician1`: `/requests/{request_id}` | Видны варианты, их правило/версия, доступность и время получения; выбор делает врач |
| 2:00–3:00 | Выбрать удалённый C001; `operator-c001` открыть связанное задание | Создано O07 с источником 1 и получателем 2; доступны единицы для подтверждения |
| 3:00–4:00 | Подтвердить одну допустимую единицу; дождаться заказа перевозки и зарегистрировать отправку | PENDING → CONFIRMED → TRANSPORT_REQUESTED → DISPATCHED; письмо источнику появляется в Mailpit |
| 4:00–5:00 | `operator-c002`: приёмка; `it1`: `/audit` и `/integrations` | Задание DELIVERED, действия видны в аудите; состояния АИСТ-М, C03 и почты доступны на экране интеграций |

Подробности, важные для воспроизведения:

1. В плане объясните разницу между целевой потребностью, защищённым запасом источника и непокрытым дефицитом.
   Наличие дефицита допустимо: алгоритм не должен скрывать нехватку или нарушать защищённый остаток.
2. В заявке выбирайте только реально предложенный удалённый вариант. Если защищённый остаток ещё неизвестен,
   дождитесь обновления данных. Отсутствие подходящего предложения не обходится ручным закреплением.
3. Сохраните идентификатор созданного задания из таблицы «Передачи по заявке». Дальше все роли открывают
   одну и ту же карточку `/tasks/{id}`. При другом источнике работает `duty1`; оператор C001 его не подменяет.
4. На PENDING выберите допустимую единицу из FEFO и нажмите «Подтвердить передачу». Повторное нажатие
   не является способом создать новое задание. Не обещайте мгновенную перевозку: CONFIRMED — ещё не ответ C03.
5. После TRANSPORT_REQUESTED оператор источника регистрирует отправку. Для синтетической RBC можно указать
   код работника `DEMO-COURIER`, температуру 4 °C, целый контейнер; время UTC оставить пустым для текущего.
   Это значения тестового примера, не инструкция по клинической перевозке.
6. После DISPATCHED приёмку регистрирует **оператор получателя**, то есть `operator-c002`, либо дежурный.
   Для обычного примера укажите 4 °C и целый контейнер, без отметки нарушения. По завершении статус DELIVERED.
7. Чтение номера случая — отдельная ссылка из заявки врача, с записью READ_PATIENT_CASE в аудит.
   `it1` показывает журнал действий, а не открытый номер случая. Mailpit используйте для письма оператору источника;
   конкретный адрес выбирается из синтетического справочника, не из личного email пользователя.

Экран заявки и карточка плана обновляются каждые 15 секунд; статус задания получает события через SSE.
Асинхронные изменения могут стать видимы после следующего обновления страницы. Открытие экрана интеграций
не подтверждает доставку всех событий Kafka или отсутствие DLT.

## Дополнительный показ: запрет использования

Выполняйте на отдельной новой синтетической заявке, не на уже принятом задании основного показа.
После отправки при приёмке отметьте «Зафиксирован выход температуры за режим в пути».
Ожидается зарегистрированная доставка с признаком запрета использования и эскалация.

Под `duty1` откройте `/duty/escalations` и карточку задания: причина нарушения остаётся видимой.
Закрытие обращения с результатом не снимает запрет использования компонентов. Этот пример показывает
реакцию системы на введённый факт нарушения, а не оценку реальных клинических условий.

## Если подготовленный путь недоступен

| Наблюдение | Действие |
| --- | --- |
| Варианта C001 нет, другой удалённый вариант допустим | Выберите фактический источник; подтверждение и отправку покажите под `duty1`, приёмку — под оператором C002 |
| Доступен только местный вариант | Покажите его отличие от перевозки. Для саги используйте подходящее PENDING-задание плана или другую новую синтетическую заявку; не утверждайте, что удалённое предложение обязано быть |
| Вариантов нет или нет свободного остатка выше защищённого | Покажите причину и дефицит; не отключайте ограничения ради демонстрации |
| Seed вернул существующую уже обработанную заявку | Создайте новую через `/requests/new`; повтор seed не является сбросом |
| CONFIRMED не меняется на TRANSPORT_REQUESTED | Сверьте `/integrations` и состояние C03; используйте [инструкцию шлюза](runbooks/gateway-unknown-failed.md), не повторяйте подтверждение ради заказа |
| «Форма устарела» | Обновите страницу в правильном профиле браузера и повторите действие с её формой |
| У источника нет формы приёмки | Войдите оператором получателя либо дежурным и проверьте DISPATCHED |
| 403 | Сверьте роль и клинику: это ожидаемый отказ, если действие чужое |

## Завершение и подтверждение показа

Зафиксируйте plan_id, request_id и O07, источники/получателя, фактические переходы и результат приёмки.
Скриншоты делайте без открытого номера случая, токенов и содержимого cookie. Отдельно отметьте,
что показали живьём, а что рассказали по диаграмме или локальному тесту.

Если нужно остановить именно этот compose-стенд без удаления томов, подготовленная команда:

```bash
docker compose -f deploy/compose/compose.yaml --env-file deploy/compose/.env --profile services --profile ui stop
```

До фактического прохождения не отмечайте браузерную и сквозную приёмку завершённой.
Оставшиеся проверки перечислены в [этапе 9](tasks/09-hardening.md) и [состоянии приёмки](perf/acceptance-status.md).
