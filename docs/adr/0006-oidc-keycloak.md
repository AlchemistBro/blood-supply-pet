# ADR-0006. Вход через OpenID Connect (Keycloak)

Статус: принят, 20.10.2026.

## Контекст

ПР6 использует собственные учётные записи (схема `access`, Spring Security). Владелец хочет OpenID Connect.
Нужны роли, привязка к клинике, опциональный второй фактор для ролей с данными K1 (NFR011, NFR016).

## Решение

Keycloak как IdP (realm `blood-supply` импортируется из JSON). `web` — OIDC-клиент с Authorization Code + PKCE, сессия в
зашифрованной cookie. Сервисы — resource servers: проверяют JWT по JWKS, читают роли и `clinic_id` из claims.
Матрица «роль → операция» общая в `libs/httpx/auth`. 2FA (OTP) для `PHYSICIAN` — флаг realm, в демо выключен.
Учётные записи ведёт ИТ-служба в консоли Keycloak; предметной роли «администратор» нет (допущение А10 каталога).

## Альтернативы

- Собственный OIDC-провайдер на Go (zitadel/dex): меньше контейнеров, но меньше узнаваемости и больше кода.
- Собственные учётные записи по ПР6: проще, но владелец явно просил OpenID.

## Последствия

Ещё один контейнер в compose и k8s; realm-файл в репозитории с демо-пользователями; интеграционные тесты авторизации
используют тестовый JWKS (`libs/httpx/auth/testing`), e2e — живой Keycloak.
