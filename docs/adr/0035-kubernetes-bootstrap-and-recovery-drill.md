# ADR-0035. Порядок запуска Kubernetes и изолированное учение восстановления

Статус: принят, 24.10.2026.

`task k8s:up` работает только с выделенным kind-кластером `blood-supply`. Сначала применяются платформа,
секреты и политики, затем ожидаются PostgreSQL и Job создания топиков. Только после этого применяются
Deployment и HPA сервисов. Разделение выполняется по метке `blood-supply.io/runtime=go-service`;
самостоятельные имитаторы остаются частью платформы. Так сервисы не создают однопартиционные топики раньше Job.

Проверка готовности проверяет службы HTTP, вход и отказ чужой роли. Исполнение NetworkPolicy проверяется
отдельным отрицательным сетевым сценарием; наличия YAML недостаточно для подтверждения сегментации.

Учение работает только в этом kind-контексте. До отказа primary создаются маркер и завершённая базовая копия.
Восстановление выполняется в отдельный кластер `pg-drill`, по времени между двумя маркерами, из архива `pg`.
Проверяются наличие первого и отсутствие второго маркера. Исходный кластер и его PVC не удаляются.
Отчёт с измерениями создаётся только реально выполненным учением; подготовленный сценарий не подтверждает RTO/RPO.

Операторы CloudNativePG и ingress устанавливаются из закреплённых URL в сценарии. Для имеющегося
`barmanObjectStore` используется API ветки CNPG 1.27; его устаревание и миграция на плагин описаны в README.
Источники: [kind configuration](https://kind.sigs.k8s.io/docs/user/configuration/),
[CNPG recovery](https://cloudnative-pg.io/docs/1.27/recovery/).
