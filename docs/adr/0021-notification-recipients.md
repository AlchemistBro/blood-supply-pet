# ADR-0021. Адресаты уведомлений — статический справочник

Статус: принят, 23.10.2026.

## Контекст

Сервис `notification` отправляет письма через почтовый сервис C04 (ИНТ-04, SMTP; в демо — Mailpit):

- оператору клиники-источника — о срочном задании на передачу по выбору врача (FR044);
- дежурному смены — об эскалации (`EscalationRaised`) и о нарушении обязательства (`TransferBroken`).

Задача этапа 7 предлагала брать адресатов из Keycloak Admin API по роли и клинике с кэшем. Для этого служебному клиенту
`notification` нужны роли `realm-management` `view-users` и `query-users`: с ними сервис читает учётные записи всех
пользователей realm, включая адреса почты и атрибуты. Это шире, чем нужно для отправки письма, а адрес личной почты
работника — персональные данные (ст. 3 Федерального закона № 152-ФЗ). Вдобавок появляется синхронная зависимость от
Keycloak на пути отправки и ещё один сценарий отказа.

Задание адресуется не человеку, а подразделению: подтвердить передачу может любой оператор клиники-источника, эскалацию
разбирает дежурная смена, а не конкретный дежурный.

## Решение

1. **Справочник адресатов статический и задаётся конфигурацией** сервиса `notification`: файл JSON по пути
   `BS_NOTIFY_RECIPIENTS_FILE`; без переменной действует встроенный демо-справочник. Справочник читается при старте,
   ошибка в нём останавливает запуск. Изменение адресов — изменение конфигурации и перезапуск.
2. **Ключ справочника — роль и клиника**, значение — адрес:
   - `CLINIC_OPERATOR` + `clinic_id` → ящик подразделения клиники, которое подтверждает передачи (отделение
     трансфузиологии). Явная запись в `operators` или, если её нет, шаблон `operator_pattern` с подстановкой
     `{clinic_code}` из справочника клиник `libs/refdata`;
   - `DUTY_OFFICER` → один ящик дежурной смены (`duty`).
3. **Адреса — служебные ящики подразделений, не личные.** Справочник принимает только адрес без отображаемого имени
   (`addr-spec` по RFC 5322): имя работника в заголовок `To` не попадает. Что за ящиком стоит подразделение, а не
   человек, — организационная мера заказчика; демо-справочник использует домен `demo.blood-supply.local`.
4. **Keycloak Admin API не используется.** Служебный клиент `notification` прав в `realm-management` не получает.
5. **Клиника без адреса** не теряет уведомление молча: запись `notification` создаётся сразу в статусе `FAILED` с причиной
   «адресат не настроен», её видит ИТ-служба в `GET /notifications?status=FAILED`.
6. **Журнал отправок** — таблица `notification`. Относительно словаря `docs/architecture/data-model.md`:
   - нет `recipient_user` (идентификатор лица не нужен, п. 3) и `body_ref` (текст письма не хранится);
   - вместо `body_ref` — типизированные поля письма: `source_clinic_id`, `target_clinic_id`, `component_kind_code`,
     `quantity`, `urgency_code`, `deadline`, `reason`. Письмо собирается из них по шаблону при отправке; поля
     свободного текста, куда мог бы попасть номер случая или фенотип, нет;
   - статусы `PENDING` / `SENT` / `FAILED` (`PENDING` вместо `QUEUED`: запись ждёт не очереди, а очередной попытки);
   - добавлены `request_id`, `recipient_role`, `recipient_clinic_id`, `source_message_id`, `next_attempt_at`,
     `last_error` (только код и текст ответа SMTP, без текста письма), `created_at`.
7. **Содержимое письма** — номер задания, клиники источника и получателя, вид компонента, количество, срочность, срок
   подтверждения, причина (для эскалации и нарушения) и ссылка на экран `web` (`BS_WEB_BASE_URL`). Фенотипа, спецификации
   замены, номера случая пациента и ФИО нет (FR044, NFR016, ADR-0011). В теме и тексте пометка «демо» (ADR-0010).
8. **Сбой почты не меняет задание** (FR044): отправка идёт после фиксации записи `notification`, вне транзакции обработки
   события; недоступный SMTP оставляет запись `PENDING` с отложенной попыткой (экспоненциальная пауза), исчерпание попыток
   или постоянный отказ сервера (код 5xx) переводит её в `FAILED`.

## Альтернативы

- **Keycloak Admin API с кэшем** — отклонено: избыточные права служебного клиента и выдача сервису личных адресов (п. 4),
  синхронная зависимость от Keycloak.
- **Атрибут `notification_email` у группы клиники в Keycloak** — те же права на чтение групп и пользователей.
- **Справочник адресатов в `libs/refdata`** — адреса меняются чаще справочника клиник и различаются по средам (демо,
  стенд заказчика); общий набор пришлось бы перевыпускать во всех базах ради одного сервиса.

## Последствия

- Уход или смена работника не требуют правки справочника: ящик принадлежит подразделению.
- Новая клиника покрывается шаблоном `operator_pattern`; отдельный ящик — запись в `operators`.
- Персональных уведомлений (конкретному врачу или оператору) нет. FR049 (уведомление врача и оператора об отказе,
  истечении срока, отмене) при необходимости адресуется так же — ящику подразделения клиники.

## Условия пересмотра

Заказчик требует уведомлять конкретного работника или хранить адресатов в каталоге организации — тогда отдельный ADR:
каталог только для чтения с минимальными правами (например, группа «получатели уведомлений» с атрибутом адреса) и запрет
личных ящиков в демо.
