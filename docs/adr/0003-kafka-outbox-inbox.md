# ADR-0003. Kafka, transactional outbox, inbox

Статус: принят, 20.10.2026.

## Контекст

Сервисы должны обмениваться событиями и командами надёжно: подтверждение без команды на перевозку (и наоборот) недопустимо;
Kafka доставляет «хотя бы один раз»; порядок сообщений по одному обязательству обязателен.

## Решение

- Apache Kafka (KRaft, один брокер в демо) как единственная шина между сервисами.
- Transactional outbox в БД каждого сервиса: событие и команда пишутся в той же транзакции, что и изменение агрегата.
- Ретранслятор читает outbox по порядку `id`, шлёт идемпотентным продюсером, останавливается на первой ошибке.
  Один активный ретранслятор на сервис (advisory lock), чтобы порядок не нарушался при нескольких экземплярах.
- Inbox в транзакции обработчика: `message_id` — первичный ключ, повтор отбрасывается.
- Ключ сообщения — идентификатор агрегата. Тип и идентификатор — в заголовках, тело — JSON по JSON Schema.
- Статус «ожидает подтверждения АИСТ-М» (ПР6) не вводится в O07: доставка ИНТ-05 — ответственность `inventory`
  (`aist_outbox_message`), O07 показывает признак через событие `PatientAllocationAcknowledged`.

## Альтернативы

- NATS JetStream: проще эксплуатация, но учебные документы и план миграции называют Kafka; для портфолио Kafka узнаваемее.
- CDC (Debezium) вместо polling-ретранслятора: имеет смысл при росте числа сервисов; сейчас polling 200 мс достаточно.
- Синхронный REST между сервисами: вернул бы распределённую транзакцию в самое критичное место (NFR004).

## Последствия

Задержка доставки до интервала ретранслятора; необходимость DLT и алертов; JSON Schema и проверка совместимости в CI.
