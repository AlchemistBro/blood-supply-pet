# Подготовка публичного демо Railway

Состояние: конфигурация подготовлена, ресурсы не создавались, образы этой версии не публиковались.
Публичного URL пока нет. Архитектурное решение и ограничения — [ADR-0026](../../docs/adr/0026-railway-demo.md).

## Состав файлов

- `profile.json` — полный перечень сервисов, источников образов, переменных, томов и видимости.
  Это инструкция для настройки проекта, **не формат импорта Railway**.
- `app.railway.json`, `edge.railway.json` — параметры deploy. Для сервисов из Docker image перенести
  значения в dashboard: не предполагать, что Railway прочитает файл из неподключённого репозитория.
- `generate.py` — воспроизводимые несекретные шаблоны из текущего realm compose; `--check` сверяет файлы.
- `prepare.py` — только локальная подготовка секретов, SQL новых баз и переменных под один опубликованный SHA-тег.
- `*/Dockerfile` — образы edge, Keycloak, PostgreSQL, Kafka, Mailpit и одноразового наполнения.
  Их публикация добавлена в существующий workflow образов. Локально Docker не запускался.

## Порядок развёртывания после согласования бюджета

1. Дождаться приёмки этапа 9 и разрешения на push. Получить зелёную сборку образов одного коммита в ghcr.io,
   проверить подписи и доступность SHA-тега всех 18 образов: 12 процессов и 6 вспомогательных образов.
   `edge`-тег для воспроизводимой установки не использовать.
2. В отдельном проекте/окружении Railway создать сервисы из образов по `profile.json`.
   Публичный домен с целевым портом 8080 назначить **только edge**. Остальные сервисы остаются без доменов
   и TCP-прокси; их имена должны совпадать с ключами профиля. Отключить автоматическое обновление образов.
3. Получив домен, локально подготовить файлы:

   ```sh
   python deploy/railway/prepare.py --public-url https://ВАШ-ДОМЕН --image-tag sha-0123456
   ```

   `prepared/` игнорируется Git и Docker. Создание каталога повторно завершается ошибкой, чтобы не заменить K1,
   cookie и пароли работающего стенда. `shared.json` содержит секреты: переносить их в shared variables
   выделенного окружения; этот файл не публиковать. Shared variables не подключать ко всем процессам автоматически:
   у каждого сервиса только перечисленные в его `*.variables.json` ссылки. K1 нужен лишь inventory и matching.
4. Запустить PostgreSQL с томом и административным паролем из подготовленного набора. Применить `prepared/init.sql`
   **только к новой выделенной установке**, вне транзакции, через `psql` с `ON_ERROR_STOP`. Создаются девять баз
   и девять ролей; существующие объекты не удаляются, при совпадении имён выполнение прекращается.
   Административную строку подключения не передавать приложениям.
5. Запустить Kafka с томом, одним стабильным `CLUSTER_ID` и listener 29092 из профиля, Mailpit и имитаторы.
   Приложения создают необходимые топики и DLT через `messaging.EnsureTopics`; автосоздание брокера выключено.
   Данные Kafka должны быть доступны пользователю исходного образа, PostgreSQL — его штатному entrypoint.
6. Запустить Keycloak и edge. Edge проверяется по `/healthz`, чтобы начальный запуск не зависел от ещё
   не готового web. `/readyz` edge отдельно проксирует готовность web. В Keycloak readiness для Railway
   проверяется по discovery realm на порту 8080; management-порт 9000 наружу не публикуется.
   Realm импортируется при первом запуске; повторный `--import-realm` существующий realm не обновляет.
7. Запустить audit, inventory, demand, planning, matching, transfer, logistics-gateway, notification и web.
   У всех `PORT=8080`, `BS_HTTP_ADDR=[::]:8080`, readiness `/readyz`, одна реплика. Не использовать shell-команду
   `sh -c` с образом приложения: в distroless нет shell. Миграции своих баз выполняют сами сервисы.
8. После готовности всех процессов выполнить образ seed один раз с политикой рестарта `NEVER`, без healthcheck
   и публичного домена. Он наполняет стенд через API; не удаляет данные и не выбирает клинический вариант.
   Начальный набор C01 и наполнение используют разные сиды; совпавшие коды единиц пропускаются.
9. Пройти сценарий README через публичный домен, проверить Secure-cookie, вход/выход, подтверждение и live-статус.
   Убедиться, что `/oidc/admin/`, `/metrics`, `/dev/` и API сервисов снаружи недоступны.
   Проверить лимиты edge, письма и аудит через закрытый доступ. Только после этого добавлять URL в README.

## HTTPS и внутренние адреса

TLS завершается на Railway. Единственный внешний issuer — `https://ВАШ-ДОМЕН/oidc/realms/blood-supply`.
Edge разрешает только realm демо и ресурсы страницы входа; административные пути закрыты.
Внутренние обращения к OIDC также проходят через **частный адрес edge**, который задаёт `X-Forwarded-Proto=https`:
это сохраняет `sslRequired=external` в realm и не полагается на классификацию приватных IPv6-адресов в Keycloak.
Адреса остальных API — прямые частные адреса сервисов; единственный служебный синхронный вызов остаётся transfer → inventory.
Весь межсервисный обмен предметными событиями использует Kafka.

Лимиты edge общие для стенда: 100 запросов/с к страницам и 10/с к входу/OIDC с burst.
Они не используют недоверенные заголовки IP как ключ. Это защита небольшого демо, а не доказательство
устойчивости к DDoS. Mailpit не отправляет письма реальным получателям и не имеет публичного домена.

## Что пока остаётся открытым

Бюджет и аккаунт, наличие опубликованных образов, фактическая совместимость с Railway, сквозная приёмка,
закрытая dev-панель, согласованный ежесуточный сброс и публичный nightly smoke не подтверждены.
Seed не является сбросом; cron, перезапускающий только seed или только C01, не обеспечивает согласованность
баз, Kafka и имитаторов. Такой cron в профиль намеренно не добавлен.
Для первичного показа можно использовать неизменённый compose/kind после разрешённого прогона.
